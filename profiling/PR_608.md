# Profile-driven performance work, and a reproducibility fix (#608)

`608_profile_refactor` → `staging` · 7 commits · 6 files, +137 / −25

Profiled a full Reference scenario (BC + CAN + CIMS + RoW, 11 years 2000–2050,
20 sectors, `max_iterations=10`) and acted on what the profile showed. Along the way
the verification turned up something more important than the speedup: **model runs
were not reproducible between processes.** That's fixed here too.

---

## Why

`model.run` is 94% of a Reference run — setup, validation and graph construction
together are under 25s of ~350s. The run makes **1.59 billion Python function calls**,
so it is bounded by interpreter overhead rather than arithmetic. The changes below all
remove per-call cost from paths that execute millions of times; none of them changes
what the model computes.

Cumulative shares from the profile (of 950s under `cProfile`; the profiler inflates
per-call overhead roughly 3×, so these rank the work rather than predict the clock):

| | calls | cumulative | share |
|---|---:|---:|---:|
| `utils/parameter/query.get_param` | 53.7M | 568s | 60% |
| `copy.deepcopy` | 133M | 298s | 31% |
| `numpy.isclose` | 1.8M | 66s | 7% |

## What changed

**`5d074cc` — nine `copy.deepcopy` calls in `emissions.py`.** `EmissionsCost.__add__`
deepcopied itself 915k times per run, plus seven more deepcopies of the same two
nested-dict shapes. `deepcopy` has to assume arbitrary object graphs, so every node pays
a memo-table lookup, an `id()` call and `_keep_alive` bookkeeping. These leaves are flat
dicts of scalars from `create_value_dict`, so `_copy3` / `_copy2` rebuild them directly:
13–16× faster per copy.

**`c23c564` — `numpy.isclose` on scalars in `market_share_limits.py`.** 1.77M calls at
~16µs each to compare two Python floats. Replaced with numpy's own scalar definition
inline, tolerances lifted to `MS_LIMIT_ATOL` / `MS_LIMIT_RTOL` at the top of the module
and set to numpy's defaults. ~145× faster per call, zero disagreements with
`numpy.isclose` over 300k samples across the `[0, 1]` domain.

**`c67d881`, `2839f1f`, `38845ad`, `f6ee3f6` — four small things inside `get_param`,**
which runs 12.9M times per run (53.7M including its previous-year recursion):

- a bitwise `&` forced a `calculation_directory` lookup on every call even though
  `do_calc` is usually False — now short-circuits;
- `inheritable_params` was a list, so membership was a linear scan — added a set beside
  it, keeping the list so `_inherit_parameter_values` iterates the same entries in the
  same order (it contains two `None`s from empty CSV rows that must not be collapsed);
- one `isinstance` was provably unreachable-as-False and is gone;
- node data now reads through `graph._node`, skipping NetworkX's `NodeView.__getitem__`
  on 54.1M lookups (77ns vs 178ns).

**`90dbe65` — reproducibility.** See below.

## Measured

`model.run`, unprofiled, same machine:

| | |
|---|---:|
| baseline | 327s / 321s |
| deepcopy + isclose | 229s |
| all six perf commits | 208s |

Roughly 30% from the first two, ~6% more from the `get_param` work.

Every configuration was compared value-by-value against the baseline across all
**58,283 stored model values**. The deepcopy and isclose changes deviate by at most
5.2e-16 — the same order as the model's own float noise — i.e. numerically free.

## The reproducibility fix

While verifying the `get_param` commits I got 226 differing values where there should
have been none. Running the **baseline against itself** explained why: 136 values moved,
one by 2e-3, with no code change at all. Pinning `PYTHONHASHSEED` made runs bit-identical,
isolating the cause to string-hash iteration order.

Tracing the ordered stream of node visits and parameter writes at two seeds and diffing
found three sites, all in `utils/graph/traversals.py`:

1. **`sg_cur = sub_graph.copy()`** inherited the node order of an `nx.subgraph` view.
   NetworkX's `FilterAtlas.__iter__` iterates the filter's own **set** of nodes — not the
   parent graph — whenever `2 * len(selected) < len(parent)`. The supply-side subgraph is
   68 of 613 nodes, so it takes that branch; the demand-side one (552 of 613) doesn't.
   `sg_cur` is bookkeeping only, so it's now rebuilt topology-only in sorted order.
2. **`possible_roots.sort(key=lambda n: len(n))`** sorts by length alone, so ties fell
   through to the view's order. Now sorts on `(length, name)`.
3. **`nx.simple_cycles`** emits cycles in a hash-seeded order *and at arbitrary rotations*.
   `loop_resolution` already sorted the cycle list, but sorting can't normalise a rotation,
   and `min`/`max` break ties by iteration order. `find_loops` now rotates each cycle to
   start at its smallest node before sorting — which also makes `model.loops` stable.

All three are required; none alone is sufficient.

**Verified:** the full 11-year run is now bit-identical across two runs with hash
randomisation left on (0 of 58,283 values differ, against 136 before), and a two-year
trace of 585,800 visits and writes is byte-identical across four hash seeds.

## Reviewer notes

- **Values shift once.** The traversal fix pins a new, deterministic order, so results
  move by up to 4e-4 relative against previous runs and are stable thereafter. Worth a
  look at scenario outputs before merging.
- **`graph._node` is private NetworkX API.** Stable across 2.x and 3.x, and the two call
  sites are adjacent, so a break would be contained and obvious. Flagging it deliberately.
- **The `_copy3` / `_copy2` helpers assume leaves hold nothing mutable.** True of everything
  `create_value_dict` produces; a list or dict added to a value dict later would be shared
  rather than duplicated. Documented at the definition.
- **`import copy` in `emissions.py` and `import numpy` in `market_share_limits.py` are now
  unused.** Left in place as a separate call.
- Any A/B measured on this branch *before* `90dbe65` — including the 6% above — was taken
  under a ~2e-3 noise floor. The 30% figure was verified at 5e-16 and is unaffected.

## Not done

`get_param` is still the largest single item at ~60% cumulative, and the structural work
is untouched: 41M of its 53.7M calls are the previous-year fallback recursing year by year
back to `base_year`, each level re-entering through the `Model.get_param` wrapper. Turning
that into a loop is where the next factor of two lives, and it needs more care than
anything here.

`_calc_all_stock` (~6%) is also untouched — `605_dcc_cache_lookups` covers it.
